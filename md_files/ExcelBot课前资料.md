# 使用大模型清洗 Excel 文件

## 清洗流程概述

使用大模型清洗 Excel 文件的核心思路是，通过 AI 识别表格结构，自动化处理复杂格式，主要分为以下三个步骤：

### 步骤一：预处理 - 解决合并单元格

1.  **解除单元格合并**：在数据处理前，首先需要解除工作表内所有的合并单元格。
2.  **填充空白值**：解除合并后，原合并区域会出现空白单元格。需要将原合并单元格的值填充到该区域的所有单元格中，以保证数据的完整性。

### 步骤二：模型分析 - 识别表头和无效信息

1.  **提取样本**：将表格的头部数据（例如前 10 行）作为样本提供给大模型。
2.  **智能识别**：让大模型根据样本判断每一行的属性：
    *   **说明性文本 (labels)**：文件标题、备注、说明等与数据无关的行。
    *   **多级表头 (header)**：由多行构成的复杂表头。

### 步骤三：自动化处理 - 清理与合并

根据大模型的分析结果，程序可以自动执行以下操作：

*   **删除说明性文本**：移除被标记为 `labels` 的行。
*   **合并多级表头**：将被标记为 `header` 的多行表头合并为单行表头，方便后续处理。

## 模型交互示例

为了让程序理解模型的意图，可以约定一个 JSON 格式作为输出。

**输入**：提供表格前N行数据。
**输出**（示例）：
```json
{
    "sheet_name1": {
        "labels": [1, 2],
        "header": [3, 4, 5]
    }
}
```

*   `"labels": [1, 2]` 指示程序：第 1 和第 2 行是说明性文本，应删除。
*   `"header": [3, 4, 5]` 指示程序：第 3、4、5 行是多级表头，需合并。


# 使用大模型生成代码注意事项

## 核心原则

*   **专注代码**：模型应直接输出可执行的 Python 代码，无需添加任何解释性文字或 Markdown 标记（如 ` ```python`）。
*   **结果导向**：所有最终的分析结果或数据展示，都必须使用 `print()` 函数输出到控制台。
*   **全面处理**：如果 Excel 文件包含多个工作表（sheet），代码需要能遍历并处理所有符合条件的工作表。

## 代码规范与要求

1.  **标准库导入**:
    *   **Pandas**: 必须使用 `import pandas as pd`。同时，为了完整显示数据，应设置 `pd.set_option('display.max_columns', None)` 和 `pd.set_option('display.max_rows', None)`。
        *   **目的**：确保在打印 DataFrame 时，所有行和列都能完整显示，避免因输出内容被截断而丢失关键信息。
    *   **Warnings**: 必须使用 `import warnings` 并通过 `warnings.simplefilter(action='ignore', category=Warning)` 屏蔽不必要的警告信息。
        *   **目的**：保持控制台输出的整洁性，让用户能专注于代码执行的核心结果，而不是被次要的警告信息干扰。

2.  **编码风格**:
    *   **命名规范**: 变量和函数命名应避免使用中文或特殊符号（如 `#`），以防范语法错误。
        *   **目的**：保证代码的兼容性和可移植性，避免因编码问题或特殊字符与语法冲突而导致的潜在错误。
    *   **保持列名**: 在处理数据时，必须保持原始列名中的特殊字符（如下划线、多空格）不变。
        *   **目的**：维持数据的原始结构和上下文，确保后续操作或用户在核对数据时，列名与源文件完全一致。

3.  **稳健性**:
    *   **异常处理**: 生成的代码必须包含 `try...except` 等异常处理机制，确保程序的稳定性。
        *   **目的**：防止程序因意外错误（如文件格式问题、数据类型不匹配）而中断执行，提高代码的容错能力。
    *   **数值转换**: 在进行数值计算（如求和、排序）前，使用 `pd.to_numeric(series, errors='coerce')` 将数据列转换为数值类型，并忽略任何无法转换的错误。
        *   **目的**：确保所有计算操作都在正确的数值类型上进行。`errors='coerce'` 会将无法转换的值设为 `NaN`（非数字），从而避免程序因个别脏数据而报错，保证了数据处理流程的顺畅。
    *   **弃用方法**: 注意 `DataFrame.fillna()` 方法的 `method` 参数已不推荐使用，应采用其他方式填充。
        *   **目的**：遵循库的最佳实践，确保代码在未来版本的 Pandas 中依然能够正常运行，提高代码的长期可维护性。


# 构建 Excel 智能体：核心流程

## 第一阶段：知识库构建与数据预处理

1.  **数据清洗与重构**:
    *   **目标**: 将各式各样的 Excel 文件转化为标准化的、可供机器读取的数据表。
    *   **原因**: 现实世界中的 Excel 表格格式混乱，常有合并单元格、多级表头等复杂情况，程序无法直接处理。标准化是实现自动化的第一步。
    *   **步骤**:
        *   **原始表 (A)**: 识别并解析 Excel 中的复杂结构，如合并单元格、多级表头等，重构后用于用户查看文件，不更改用户的原始文件。
        *   **重构表 (B)**: 利用大语言模型（LLM）将非结构化或半结构化的原始表 (A) 清洗并重构为标准的二维数据表 (B)，确保数据格式的统一和准确性。

2.  **元数据提取与索引**:
    *   **目标**: 为每个数据表创建一份“说明书”（元数据），方便后续快速检索和理解。
    *   **原因**: 如果没有这份“说明书”，当用户提问时，系统需要逐一打开并读取所有文件才能找到相关信息，效率极低。元数据索引能帮助系统秒级定位。
    *   **步骤**:
        *   **内容摘要 (Summary)**: 对每个 Excel 文件的内容和用途生成简明扼要的总结。
        *   **建立索引**: 将所有文件的内容摘要整合，构建一个可供快速检索的知识库。

## 第二阶段：交互式分析与代码生成

1.  **意图理解与文件定位**:
    *   **目标**: 当用户提出问题时，快速锁定最相关的数据文件。
    *   **原因**: 避免盲目地在所有文件中进行分析。利用第一阶段创建的索引，可以先将搜索范围缩小到最相关的一两个文件，大幅提升效率和准确性。
    *   **步骤**: 接收用户输入的问题，通过语义搜索在知识库的“内容摘要”中进行匹配，精准定位到一个或多个最相关的 Excel 文件。

2.  **动态分析与方案规划**:
    *   **目标**: 在生成代码前，动态解析数据并与用户确认分析方案。
    *   **原因**: 确保生成的代码能够准确处理特定文件的数据结构。同时，通过与用户确认分析步骤，可以避免因理解偏差导致无效或错误的操作。
    *   **步骤**:
        *   **动态提取结构信息 (Schema)**: 针对定位到的文件，实时提取其重构表 (B) 的关键结构信息，包括表头、每列的数据类型、数据样本（如前5行和后5行）等。
        *   **构建上下文 (Context)**: 将动态提取的“结构信息”（Schema）作为上下文，连同用户的问题一起提供给大语言模型。
        *   **生成分析计划**: 大模型基于上下文，提出一个清晰查询指令，说明它将如何操作数据来回答用户的问题（例如，“北京的可乐销售情况怎么样” ——> "筛选出表单中"城市"为"北京"且"产品系列"为"可口可乐"的所有行数据，并统计其"销售数量"、"总销售额"和"净销售额"的总和。"）。
        *   **用户确认**: 将此分析计划呈现给用户，由用户确认或提出修改意见。

3.  **代码与伪代码生成**:
    *   **目标**: 基于确认后的分析计划，生成可执行的代码和易于理解的伪代码。
    *   **原因**: 核心是自动化执行数据分析任务。同时生成伪代码，即使用户不懂编程，也能理解系统的操作逻辑，增强了整个过程的透明度。
    *   **步骤**:
        *   **生成 Python 代码**: 在获得用户确认后，大模型动态生成用于数据查询、计算或可视化的 Python 代码。
        *   **生成伪代码**: 根据刚生成的 python 代码生成一份逻辑步骤清晰的伪代码，帮助用户理解代码的核心操作。

## 第三阶段：执行、溯源与结果呈现

1.  **安全执行与结果生成**:
    *   **目标**: 使用jupyter内核运行代码，得出分析结果。
    *   **步骤**:
        *   **代码执行**: 执行由 LLM 生成的 Python 代码，操作重构后的数据表 (B)。
        *   **结果总结**: LLM 对代码的原始输出（如数据、表格）进行解读和总结。

2.  **数据溯源与验证**:
    *   **目标**: 提高分析过程的透明度，方便用户进行数据验证。
    *   **原因**: 建立用户对结果的信任。通过清晰地展示结果来源于哪些数据、经过了哪些计算步骤，用户可以轻松验证分析的准确性。
    *   **步骤**:
        *   **字段回溯**: LLM 分析已执行的代码，识别出结果所依赖的关键数据字段和源数据，并将它们明确展示给用户。

3.  **结果呈现**:
    *   **目标**: 将所有分析信息以清晰、友好的方式呈现给用户。
    *   **原因**: 提供一个完整的、可信的、易于理解的答案。用户不仅能看到最终结论，还能了解分析的全过程，满足不同层次的审查需求。
    *   **步骤**: 可向用户完整地展示：最终结论、结果总结、生成的可视化图表、伪代码与源代码，以及数据溯源信息。


# 将大模型输出实时展示到前端

## 核心技术：Server-Sent Events (SSE)

为了实现大模型生成内容的实时“打字机”效果，我们采用 SSE（服务器发送事件）技术。这是一种允许服务器向客户端单向推送数据的 Web 技术。

*   **工作原理**：后端通过一个持久化的 HTTP 连接，持续地将数据块（events）发送给前端。
*   **实现方式**：在后端，通常通过返回一个 `Content-Type` 为 `text/event-stream` 的流式响应（Streaming Response）来实现。
    *   *示例：* `Response(stream_generator(), content_type='text/event-stream')`

## 数据格式化与传输

SSE 有固定的消息格式。每个消息都以 `data:` 开头，以 `\n\n` 结尾。为了传输复杂的结构化信息，我们通常将数据包装成 JSON 字符串。

### 1. 封装响应数据包

我们定义一个辅助函数 `to_ret_s_suc`，它专门负责将核心数据打包成符合前端要求的 JSON 格式，并封装为 SSE 消息。

```python
import json

def to_ret_s_suc(answer, finished, content_type, content_status, chat_id=None, response_id=None):
    """
    将核心数据格式化为 SSE 事件流。
    """
    # 1. 构建只包含必要字段的字典
    payload = {
        'answer': answer,
        'finished': int(finished),
        'content_type': content_type,
        'content_status': content_status,
        'chat_id': chat_id,
        'response_id': response_id,
    }
    
    # 2. 将字典转换为 JSON 字符串，并格式化为 SSE 消息
    # suc() 是一个假设的函数，用于包装标准成功响应
    sse_message = "data: {} \n\n".format(json.dumps(suc(payload)))
    return sse_message
```
*   **关键字段解析**：
    *   `answer`: 当前数据块的内容（例如，代码或文本片段）。
    *   `finished`: 标志位，`0` 表示流仍在进行中，`1` 表示流已结束。
    *   `content_type`: 告诉前端当前内容的类型，如 `code` 或 `text`，否则前端无法判断渲染方式。
    *   `content_status`: 告知前端当前内容块的处理阶段，如 `start` (开始), `in_progress` (进行中), `end` (结束)。
    *   `chat_id` / `response_id`: 用于追踪会话和响应的唯一标识符。

### 2. 使用 `yield` 发送数据流

在后端的处理逻辑中，我们使用 `yield` 来分块发送数据。

```python
# --- 在流式响应函数中的使用示例 ---

# ... 代码生成或处理逻辑 ...

# 示例1：发送一个 "处理中" 的状态消息，此时 answer 为空
yield to_ret_s_suc(
    answer='', 
    finished=0, 
    content_type='code', 
    content_status='start',
    chat_id=chat_id,
    response_id=response_id
)

# ... 循环生成内容并持续 yield 数据块 ...
# yield to_ret_s_suc(answer=partial_code, finished=0, ...)

# 示例2：发送最后一个包含最终结果的消息，并设置 finished=1
yield to_ret_s_suc(
    answer='...final_result...', 
    finished=1,
    content_type='code',
    content_status='end',
    chat_id=chat_id,
    response_id=response_id
)
```

### 3. 前端解析与自定义

*   **前端处理**：前端通过监听 `EventSource` 的 `message` 事件来接收数据流，并根据 `content_type`、`content_status` 等字段来决定如何展示数据。
*   **灵活扩展**：虽然我们只保留了核心字段，但这个结构可以根据业务需求与前端约定进行灵活扩展，添加更多自定义字段。

### 4. 应用示例：一个完整输出流程的生命周期

在一个完整的Excel分析任务中，后端可能会依次生成并发送多种不同类型的内容。通过组合 `content_type` 和 `content_status`，我们可以清晰地定义每个阶段，让前端能够精确地控制对话过程中不同的渲染方式。

以下是一个典型的三阶段流程：**生成代码** -> **执行并返回数据** -> **生成最终结论**。

#### 阶段一：生成代码 (`content_type: 'code'`)
1.  **开始 (`content_status: 'start'`)**: 后端发送第一个信号，通知前端准备一个用于显示代码的UI组件（例如，一个代码块）。此时 `answer` 字段为空。
2.  **进行中 (`content_status: 'in_progress'`)**: 后端持续发送代码片段，`answer` 字段包含这些片段。前端接收到后，实时地将它们追加到代码块中，形成“打字机”效果。
3.  **结束 (`content_status: 'end'`)**: 代码生成完毕。后端发送一个结束信号，前端可以完成UI操作（例如，激活“复制代码”按钮）。

#### 阶段二：返回数据 (`content_type: 'data'`)
1.  **开始 (`content_status: 'start'`)**: 代码执行完毕后，后端通知前端准备一个用于展示表格数据的组件。
2.  **进行中 (`content_status: 'in_progress'`)**: 后端将执行结果（例如，一个DataFrame的片段）流式发送回来。
3.  **结束 (`content_status: 'end'`)**: 数据全部发送完毕。

#### 阶段三：返回结论 (`content_type: 'result'`)
1.  **开始 (`content_status: 'start'`)**: 数据分析完成后，后端通知前端准备一个用于显示最终文字结论的区域。
2.  **进行中 (`content_status: 'in_progress'`)**: 后端流式地发送最终的分析结论文本。
3.  **结束 (`content_status: 'end'`)**: 结论发送完毕。此时，通常会同时在最后一个数据包中将 `finished` 字段设为 `1`，彻底关闭本次SSE连接。
